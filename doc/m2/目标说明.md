## 1. 本仓在 M2 中交付什么

`baron-klinecharts` 为 M2 提供通用、可版本化的图表表达和交互能力：

- 线性/对数价格轴切换；
- 水平固定价格线的精确编辑；
- 量度涨幅工具；
- 整体移动、锚点拖动、样式编辑和精确命中；
- 完整交互过程事件；
- 通用宿主动作边界；
- Scene 导出、销毁、重建和恢复；
- npm/Python 正式制品。

本仓不理解“颈线”“量度目标”“候选”“确认”“结构轮次”“突破”或“完成度”。这些语义完全属于 `my-cage`。

## 2. M1 已有基线

M1 已形成并发布：

- Scene Schema、canonical JSON/hash 和 Python 同步；
- KLineCharts Adapter；
- Web Runtime 与基础工具栏；
- 蜡烛图、`horizontalStraightLine`、稳定 Overlay ID 和数据坐标；
- 水平直线只保存有限 `anchor.value`，不保存无意义 timestamp；
- 创建、导出、销毁、重建和恢复浏览器验证；
- Python `baron-klinecharts==0.1.0`；
- npm Scene `0.1.0`、Adapter/Runtime `0.1.1` 正式制品。

Task 0 必须核对引擎当前已经具备但尚未公开的能力，避免重复实现；同时不能把“引擎内部偶然可用”当作稳定 Scene/Runtime 契约。

## 3. 线性/对数坐标目标

- 价格轴模式必须是明确 Scene 配置，不能依赖运行时默认值；
- Runtime 能够切换线性与对数模式；
- 导出、恢复和重建后保持相同模式；
- 固定业务价格的数据值在两种坐标下不变；
- 交互计算必须通过数据坐标转换，不能把屏幕像素保存为业务锚点；
- 对数轴遇到非正价格时明确失败，不能静默切换到线性轴；
- 坐标切换只改变显示映射，不改变 Overlay ID、价格或 metadata。

## 4. M2 正式图形能力

### 4.1 水平固定价格线

沿用 M1 的正式水平直线能力，并补齐：

- 选择和取消选择；
- 精确命中；
- 整线垂直拖动；
- 数值方式更新；
- 颜色、线宽和实/虚线样式编辑；
- 拖动过程事件；
- Scene 恢复后价格、样式和稳定 ID 不变。

水平线在 `my-cage` 中可能被确认为颈线或目标，但本仓只把它当普通 Overlay。

### 4.2 量度涨幅工具

M2 量度工具最低需要：

- 两个明确数据锚点；
- 展示起点价格、终点价格、绝对变化和百分比变化；
- 正涨幅、零变化和负变化的确定显示语义；
- 整体移动时保持原价格差或百分比语义，具体模式由 Task 1 契约唯一确定；
- 单独拖动任一锚点；
- 在线性/对数坐标下都使用原始数据值计算读数；
- 导出和恢复后读数一致；
- 价格、时间、样式和稳定 ID 使用 canonical Scene 表达。

量度工具只帮助用户确定候选目标，不自动创建业务目标价，也不直接触发确认。

## 5. 精确命中与编辑

M2 需要正式定义并测试：

- 线主体命中区域；
- 锚点命中区域与优先级；
- 多个重叠 Overlay 的选择顺序；
- 整体拖动与锚点拖动的区分；
- 拖动开始、过程、提交和取消；
- Escape、失焦、销毁和 Scene 重载时的状态收敛；
- 编辑失败时最后一个已确认 Scene 不丢失；
- 图表缩放、滚动和 resize 后命中与数据坐标仍正确。

具体像素阈值由 Task 0/Task 1 根据现有实现和浏览器测试冻结，目标文档不提前猜测。

## 6. Runtime 事件与宿主动作

正式 Runtime 事件至少覆盖：

- Overlay 创建完成；
- 选择变化；
- 拖动开始；
- 拖动过程；
- 拖动提交；
- 样式变化；
- 删除/归档意图；
- Scene 或 Overlay 更新失败；
- 通用宿主动作，例如针对当前 Overlay 请求打开业务操作。

事件 payload 必须包含稳定 Overlay ID、必要的数据坐标、操作阶段和 Runtime/Scene 版本。事件不能携带 `neckline`、`price_version`、`structure_id` 等 `my-cage` 业务字段作为正式图表语义；业务系统可以通过 opaque metadata 维护自己的关联。

## 7. Scene 与版本兼容

- 新增能力优先采用向后兼容的 schema 扩展；
- 若必须升级 Scene version，需要明确迁移和拒绝规则；
- 旧 M1 Scene 必须继续加载和恢复；
- 新 Scene 不能被旧 Runtime 静默错误解释；
- Python 模型、JSON Schema、TypeScript 类型和 Runtime 必须同步；
- canonical hash 只由规范化 Scene 内容决定；
- 生成代码使用仓库现有脚本，不能手改生成物而跳过源 Schema；
- 正式版本号在 Task 0/Task 1 根据受影响包和 registry 现状确定。

## 8. 对外正式产物

M2 预计影响并重新发布：

- `@baron1996/kline-scene-schema`；
- `@baron1996/klinecharts-adapter`；
- `@baron1996/klinecharts-runtime`；
- `baron-klinecharts` Python 包；
- 必要时同步受契约影响的 CLI/Render Runtime。

只发布确实受影响的包，但版本矩阵必须能证明兼容组合。不得覆盖已发布版本。

## 9. 本仓不包含

- 价位候选和确认业务流程；
- 价格版本、结构轮次或回放结果；
- 突破和完成度计算；
- 主指数绑定或金融数据请求；
- `my-cage` 专属 API；
- M3 指标、折线、全屏和十字线能力，除非 Task 0 证明它们是 M2 已有交互的不可分前置；
- M6 完整绘图矩阵；
- 第二图表引擎或业务仓临时绘图实现；
- Git、发布或部署的默认授权。

## 10. 阶段门

### BK-M2-0：校准门

- 当前包版本、Scene、Runtime、Adapter、引擎能力和脏工作区已记录；
- 复用点、真实缺口和精确文件图已形成；
- 输出 `执行前校准报告.md`。

### BK-M2-1：契约门

- M1 Scene 向后兼容策略明确；
- `my-cage` 不需要依赖内部引擎对象。

### BK-M2-2：仓内能力门

- Schema、Adapter、Runtime、Python、canonical、浏览器和视觉回归通过；
- M1 fixture 不回退。

### BK-M2-3：正式制品门

- npm/Python 新版本从 registry 干净安装；
- 版本、tag、Release、integrity、hash 和 provenance 一致；
- 干净消费者浏览器验证通过。

## 11. 停止条件

出现以下情况必须停止并回报总 session：

- M2 必须使用另一个图表引擎才能实现；
- 需要把业务语义写入正式 Scene/Runtime 契约；
- 引擎无法提供数据坐标或可靠事件，必须修改范围；
- 新契约会破坏 M1 Scene 且迁移策略未确认；
- 需要手改生成文件而无法从 Schema 生成；
- 需要 Git、registry、tag 或 Release 写操作但尚未授权。
